How to Use This Tool

Field reference & formula guide

ⓘ Overview

This tool does two things:

  • Scanner sizing — estimates how many Qualys scanner appliances you need to scan a given set of targets in one parallel pass, with a parallelism tradeoff table showing speed vs. resource options.
  • Scan Time Planner — given a time window (e.g. 10h overnight) or an existing scanner pool, shows which scanner spec and count will meet your goal, and how long your current setup will actually take.

Scan Configurations

Scan Type

  • VM — Vulnerability Management host scan. Uses target IP count.
  • PC — Policy Compliance scan. Uses target IP count. Higher scan cost per slice than VM.
  • PCI — PCI DSS compliance scan. Uses target IP count. Same slice cost as VM but significantly longer per-burst time (~60–120 min vs 5–10 min for VM/PC).
  • MAP — Discovery / network mapping scan. Uses job count instead of IPs.
  • WAS — Web Application Scanning. Uses job count. Fixed capacity constants apply.

Alive IPs to Scan in Parallel (VM / PC / PCI)

These are the alive IPs that will be scanned in parallel. Obtain from a MAP scan or a network ping sweep.

Number of Scan Jobs (MAP / WAS only)

One job per scan target (web app or network segment). Each job is dispatched independently to the scanner.

Scanner Appliance Configuration

Scanner Type

  • Virtual / Container (Internal) — VM-hosted internal scanner. A 40% virtual penalty (×3/5) is applied to the estimated capacity, on top of the 40% Hyperthreading / SMT penalty when HT is enabled.
  • Virtual Perimeter — VM-hosted perimeter scanner, no hypervisor penalty.
  • Physical 6120-B1 (NVXE) — Fixed hardware appliance, 1,245 units.
  • Physical 6120-A1 (NVX) — Fixed hardware appliance, 1,040 units.

Base CPU Speed (MHz)

Clock speed of a single CPU core as seen by the scanner. Typical range: 2500–2900 MHz. Default: 2600 MHz. Key inputs used in capacity estimation: CPU count, CPU speed (MHz), and available RAM. CPU speed is often the bottleneck. It can be read from the VM's CPU spec in your virtualization platform (VMware, AWS, Azure, Oracle Cloud, etc.) — without needing to deploy or boot the scanner VM — and is also visible in the scanner's boot logs. Note: users have no direct control over CPU speed; it is determined by the underlying host hardware and hypervisor allocation.

Hyperthreading / SMT (HT)

When enabled, a 40% penalty (×3/5) is applied to the total effective CPU speed. HT (also known as SMT — Simultaneous Multi-Threading) is on by default for most VMs and is auto-detected by the scanner daemon at boot. The HT status can be found in the VM's CPU spec on your virtualization platform or in the scanner's boot logs — no scanner deployment needed to check it. Some platforms (e.g. VMware, Oracle Cloud) allow HT to be toggled per VM; others do not expose this control. Disable this only if confirmed hyperthreading=0 in the scanner's boot logs or VM settings.

vScanner CPUs & Memory — CPU:RAM sizing

Ideal ratio is 1 vCPU : 2–3 GB RAM (max 1:4). Recommended tiers:

  • Min stable: 2 vCPUs / 4 GB RAM
  • Small–Medium: 4 vCPUs / 8 GB RAM
  • Enterprise: 8 vCPUs / 16 GB RAM and above

External Scanners to Use — Perimeter type only

The number of Virtual Perimeter scanners available in your pool (default: 40). The Scan Time Planner uses this as a hard cap — the Scanners for Goal column will never suggest exceeding this count, and the “add scanners” recommendation will flag when reaching the goal would require more than your defined limit.

Scan Performance Settings

Parallel Host Scans per Scanner per Slice (P) ▶ drives slice & job math

Set in the Scan Performance settings in your Option Profile. Range: 1–50. Recommended default: 30. P defines how many target IPs are scanned concurrently within one slice. A scanner handles one slice per job at a time — to run more slices in parallel on the same scanner, split large jobs into multiple smaller jobs. Avoid extreme P values (e.g. 50) unless scanners are well-resourced and the network can handle it.

Parallel ML Scaling (ON / OFF)

When ON, the Qualys ML engine spawns 3×P parallel processes per scanner. Recommended: OFF by default. Enable only if your scanners are adequately sized and the environment is validated for high-parallelism loads. Match this setting to what is configured in your Option Profile.

Jobs, Slices & Parallelism

What is a slice?

A scan job is divided into one or more slices, each covering up to P target IPs. Total slices = ceil(Target IPs ÷ P). Each slice is dispatched to a scanner as a unit of work.

One slice per job at a time

A scanner is assigned one slice per job at a time. To run more slices in parallel on the same scanner, split large jobs into multiple smaller jobs — each job contributes one slice to the scanner simultaneously, increasing throughput without adding hardware.

Bursts

A burst is one pass where all scanners process their assigned slices in parallel. Bursts needed = ceil(Total Slices ÷ (Scanners × Max Slices per Scanner)). When all slices fit in one burst, all target IPs are being scanned simultaneously.

Understanding the Results

Scanners Needed — Trade-off Table (VM / PC / PCI)

For VM/PC/PCI scans, the large blue card shows four strategies for completing the workload. Pick the row that fits your scan window.

  • ⚡ Fastest — full pool, completes in 1 burst. Maximum scanners, minimum duration.
  • ⚖ Balanced — 75% of the pool, good middle ground.
  • 💰 Economical — 50% of the pool, fewer scanners.
  • 🐢 Minimal pool — 25% of the pool, lowest footprint, longest duration.

For MAP/WAS, a single scanner count is shown (jobs are dispatched 1-per-target).

Jobs to Create

The minimum number of scan jobs to create to achieve a row's stated duration. Because a scanner runs one slice per job at a time, splitting your scan into more jobs lets each scanner work on more slices in parallel. The tool computes the smallest job count that still hits the row's round count — splitting further doesn't help that strategy. This value is also capped by the Concurrent Scans and Maps limit, since you can't run more jobs at once than that. Keep in mind that Jobs to Create is one of several levers — you may also need to adjust your scanner pool size or scanner specs (CPU / RAM) to meet your scan window.

Max Slices in Parallel / Scanner

How many simultaneous slices (one per concurrent job) a single scanner can handle at once. Driven by scanner capacity, CPU speed, and ML Scaling setting — then capped by the Concurrent Scans and Maps limit (you can't run more jobs/slices than that across the pool).

Total Slices

Total number of slices required to cover all target IPs = ceil(Target IPs ÷ P). This is the total unit of work to be distributed across the scanner pool.

Estimated Scan Duration

Each row's duration ≈ bursts × avg time per burst (ballpark): ~5–10 min for VM/PC, ~60–120 min for PCI. Actual speed varies by: number of open ports, scan settings (port range, authenticated vs. non-authenticated), target network connectivity and response speed, and number of vulnerabilities to detect and process.

Scanner Pool & Load Best Practices

Spread the load

The scanner count shown represents the minimum needed for maximum parallelism in one pass. For better cost-efficiency, spread jobs across multiple scan windows and reduce extreme parallelism settings. Fewer scanners running longer is often more sustainable than many scanners peaking simultaneously.

Keep your scanner pool uniformly sized

All scanners in a pool should have the same vCPUs, RAM, and type (all virtual or all physical). Mixed-spec pools create uneven capacity, wasted slots, and unpredictable scan times — the weakest scanner becomes the bottleneck.

Disk — recommended 100 GB for large scans

The default disk size works well for most small to medium scans. For large or frequent scans, provision at least 100 GB. If you hit "disk full" errors, increase disk allocation. Disable the Debug Scan setting in the Qualys portal before scheduling scans — it dramatically inflates disk usage and can render a scanner unusable.

Scan Time Planner

Overview

The Scan Time Planner appears inside the main blue card when you enter a Desired Scan Duration or Scanner Pool Size. It shows a table across standard scanner specs plus your current config. Average scan times are predefined per scan type (VM/PC: ~7.5 min/round, WAS: ~10 min/job, PCI: ~60 min/round, MAP: ~25 min/job).

Desired Scan Duration

How long you have to complete the scan — enter in hours or minutes using the toggle next to the input (e.g. 10 hrs for an overnight window, or 60 min for a short batch). Activates the Scanners Needed column, showing the minimum scanner count to meet your duration at each spec. Uses the predefined average time for the selected scan type. For Perimeter type, the count is capped at your External Scanners to Use limit (a small “max” badge appears when capped).

Scanner Pool Size

Optional — enter your current scanner count to unlock the spec comparison view, which shows how upgrading specs would change estimated total scan time for your existing pool.

  • Rounds — how many rounds the scan would take at each spec tier with your current pool.
  • Est. Duration — rounds × the predefined avg time for the scan type.
  • vs Current — % faster (▼ green) or slower (▲ red) relative to your config row.
  • Your Config row — when a Desired Scan Duration is set, this row's Est. Duration reflects your actual pool count (labelled “with your N scanners”), while preset rows show the time at the scanner count each would need to hit the goal.

Smart Recommendations

When a Desired Scan Duration is set with an existing pool, the planner assesses your current spec against the goal and offers clear options:

  • ✅ / ⚠️ Pass / short verdict — if short, it states how many scanners short you are at your current spec.
  • Add scanners — minimum extra scanners of your current spec to meet the goal (capped at External Scanners to Use for Perimeter).
  • Upgrade spec — smallest standard tier that meets the goal with your existing pool count.
  • Split the target list — break the scan into smaller target lists to fit the window without changing scanners.
  • Enable ML Scaling (×3) — projects impact of turning on Parallel ML Scaling without any hardware change.

How spec affects total scan time

A larger scanner spec increases Max Jobs per Scanner (more slices processed per round). More slices per round → fewer rounds → lower total time, even if per-round wall-clock time stays the same. Per-round time is driven by network topology and scan option profile, not scanner spec. Note: the Concurrent Scans and Maps limit caps Max Jobs per scanner — once a spec reaches that cap, a larger spec won't reduce time further until you raise the limit (or add scanners).

Disclaimer

All outputs are ballpark estimates based on standard scan profile settings, recommended scanner sizing, and normal target network conditions — with this assumed to be the only active scan on the scanner. A concurrent scan on the same scanner will reduce throughput. Actual performance also varies by: network topology, firewall rules, host responsiveness, and hypervisor resource contention. Always validate with a pilot scan before production rollout.
